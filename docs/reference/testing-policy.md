# 测试与验证约束

本项目为应用型工程，测试不是默认的开发产物。除非存在明确的测试价值，否则不得新增
`tests/`、unit test、smoke test、fixture、mock 或其他测试基础设施。

## 默认原则

- 优先通过现有生产代码、现有入口、现有脚本、现有 launch、仿真或实际运行链路完成验证。
- 修改已有模块时，优先在现有模块和现有执行路径中验证，不得为验证而复制一套独立测试逻辑。
- 不得因为“工程规范”“最佳实践”“提高覆盖率”或“测试完整性”而主动增加测试。
- 小型项目允许没有 `tests/` 目录。没有实际测试需求时，不得创建该目录。

## 只有以下情况允许新增测试

满足至少一项实际需求时才考虑创建独立测试：

1. 纯算法、数学计算、解析器、状态机等可独立验证的核心逻辑；
2. 已经出现并需要防止复发的 bug；
3. 现有运行链路无法稳定、快速、确定地验证某个关键行为；
4. 项目已有明确的 CI 自动化测试要求；
5. 用户明确要求增加测试。

除上述情况外，禁止新增独立测试文件。

## 禁止的测试

禁止创建以下类型的测试：

- 仅为了调用一次生产函数；
- 仅为了增加代码覆盖率；
- 只是把现有函数复制/提取成 `test_xxx()`；
- 没有明确输入、输出和失败条件的 smoke test；
- 不可独立执行且没有自动化价值的测试；
- 与生产代码重复实现相同逻辑的测试；
- 仅验证简单 getter/setter、参数转发、ROS 2 胶水代码、简单 callback 或简单封装；
- 为了测试方便而引入 mock、fake、fixture、interface、factory、dependency injection 等额外架构。

## 测试位置

- `tests/` 仅存放真正需要自动化执行的测试。
- 用户可直接运行的实例、调试程序、实验脚本、模块验证入口，不得放入 `tests/`。
- 需要人工运行验证的内容，优先复用现有入口或放入现有 `scripts/`、`examples/`、`tools/`。

## 新增测试前的判断

创建测试前必须先判断：

- 现有运行入口是否已经能够验证该行为；
- 为什么现有模块不能直接验证；
- 该测试具体防止什么错误；
- 测试失败时能提供什么实际信息。

如果无法明确回答以上问题，不得创建测试。

## 测试与生产代码

- 测试必须调用现有生产接口，不得复制生产逻辑。
- 不得为了提高可测试性而改变生产架构。
- 测试基础设施不得增加项目复杂度。
- 测试数量不是工程质量指标。

## 验证优先级

实际运行验证优先于自动化测试：

1. 现有程序入口；
2. 现有脚本 / launch；
3. 模块间集成运行；
4. 仿真或实际硬件验证；
5. integration test；
6. unit test。

不得默认从第 6 项开始。
